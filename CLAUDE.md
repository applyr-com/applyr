# Applyr — Claude Code Context

## What is Applyr?
Applyr is a scholarship auto-application platform. Students fill out their profile once, the app finds matching scholarships, and generates tailored essays for each one using their saved experiences. The core insight is that existing tools stop at search — Applyr handles the execution.

## Tech Stack
- Frontend + Backend: Next.js 16 (App Router, TypeScript)
- Database: Supabase (Postgres)
- Auth: Supabase Auth
- AI: Anthropic API (Claude Sonnet)
- Styling: Tailwind CSS + shadcn/ui
- Hosting: Vercel
- Repo: github.com/applyr-com/applyr

## Database Schema
Six tables:

**users** — mirrors Supabase auth.users
- id (uuid, PK, references auth.users)
- email (text, unique)
- name (text)
- created_at (timestamp)

**profiles** — stores student profile data for matching
- id (uuid, FK → users.id)
- major, gpa (decimal), state, year (int), school
- first_gen (boolean), financial_need (boolean)
- ethnicity, gender (optional)
- updated_at (timestamp)

**experiences** — STAR-format experiences for essay generation
- id (uuid, PK)
- user_id (FK → users.id)
- category (text) — Leadership, Community Service, Work/Internship, Research/Academic, Extracurricular, Personal Growth
- title, situation, task, action, result (text)
- tags (text[])
- created_at (timestamp)

**scholarships** — both seeded and user-added scholarships
- id (uuid, PK)
- name, organization (text)
- amount (integer), deadline (date)
- renewable (boolean)
- major (text) — CS, Engineering, Any, etc.
- gpa_min (decimal), eligibility (text)
- essay_prompt (text)
- tags (text[])
- url (text)
- is_custom (boolean) — false for seeded, true for user-added
- created_by (uuid, nullable FK → users.id)
- created_at (timestamp)

**applications** — join table between users and scholarships
- id (uuid, PK)
- user_id (FK → users.id)
- scholarship_id (FK → scholarships.id)
- status (int) — 0=saved, 1=inprogress, 2=submitted, 3=won, 4=rejected
- match_score (integer, 0-100)
- saved_at, updated_at (timestamp)

**essays** — versioned essay drafts per application
- id (uuid, PK)
- user_id (FK → users.id)
- application_id (FK → applications.id)
- content (text)
- word_count (integer)
- version (integer) — increments on each regeneration
- created_at, updated_at (timestamp)

## Features to Build (MVP)

### Week 2 — Profile & Matching
- Profile setup form at /profile/setup (saves to profiles table)
- STAR experience interview UI — conversational, one question at a time
- POST /api/experiences/extract — sends 4 STAR answers to Claude, returns structured JSON
- Experience confirmation screen — shows extracted STAR summary, user edits and saves
- Scholarship browse page at /scholarships — search, filters, match score display
- POST /api/scholarships/match — Claude scores each scholarship 0-100 based on profile fit
- Wire match scores to browse page, sort by score

### Week 3 — Essay Generation
- POST /api/essays/generate — Claude drafts essay from prompt + profile + experiences
- Essay editor at /scholarships/[id]/essay — draft, word count bar, tone selector, refine input, regenerate, status selector
- POST /api/essays/refine — Claude rewrites essay based on user feedback
- Save essays with version tracking
- Dashboard at /dashboard — stats, pipeline, activity, profile completeness
- Your Scholarships page at /my-scholarships — saved scholarships, status management
- Add Custom Scholarship modal
- Experiences list page at /experiences

### Week 4 — Polish & Beta
- Loading states on all Claude API calls
- Error handling on all API routes
- Mobile responsive all pages
- Empty states for all pages
- Applyr logo and favicon
- Deploy and beta test with 10 Purdue students

## Key Product Decisions
- STAR method for experience capture — conversational interview, AI structures behind the scenes
- Three pricing tiers: Free (10 matches, 2 essays/mo), Pro ($19/mo unlimited), Concierge ($199 one-time)
- Purdue-first user acquisition strategy
- No auto-submit in v1 — essay generation and tracking only
- Match score (0-100) stored in applications table, generated by Claude

## Code Style Preferences
- TypeScript throughout
- 'use client' only when component needs useState, useEffect, or event handlers
- Server components by default
- Supabase client from lib/supabase.ts (browser) or lib/supabase-server.ts (server)
- All API routes in app/api/
- Shared components in components/
- Keep components small and focused
